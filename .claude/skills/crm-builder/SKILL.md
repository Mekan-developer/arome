# CRM Builder

Задача скилла — две вещи сразу:

1. **Backend-скелет всегда одинаковый и предсказуемый** (слои, тесты, миграции). Это скучная часть, и она должна быть скучной.
2. **UI всегда разный.** Не «разный оттенок синего», а разный по структуре, типографике и логике интерфейса. Две CRM, сделанные по этому скиллу, не должны опознаваться как работа одного шаблона.

Порядок работы: сначала бриф → дизайн-направление → проверка на шаблонность → и только потом код. Если начать с кода, UI неизбежно скатится в дефолт.

**Важное разделение.** Есть ремесло и есть стиль, и путать их нельзя:

- **Ремесло — константа.** Плотность, состояния при наведении и фокусе, поведение массового выделения, тени только у плавающих слоёв, табличные цифры, три разных пустых состояния. Это одинаково хорошо во всех проектах и описано в `references/craft-baseline.md`. Читать при каждой работе над интерфейсом.
- **Стиль — переменная.** Палитра, шрифты, компоновка, сигнатурный элемент. Меняются от заказчика к заказчику, описаны в `references/ui-directions.md`.

Заказчик отличает твою систему от чужой по стилю, а платит за неё — за ремесло. Нужно и то, и другое: уникальный, но неряшливый интерфейс проигрывает аккуратному шаблону.

## Шаг 1. Бриф (5 вопросов, не больше)

До кода нужно знать:

- **Домен.** Автосервис? Клиника? Логистика? Юрфирма? Строительная бригада? Это главный источник дизайн-решений.
- **Кто сидит в системе целый день.** Менеджер за большим монитором, мастер с телефона в цеху, диспетчер с двумя экранами — разные интерфейсы.
- **3–5 сценариев, ради которых система существует.** «Принять заявку → назначить мастера → закрыть акт» важнее, чем список из 40 фич.
- **Главная сущность.** Сделка? Заявка? Пациент? Рейс? Вокруг неё строится всё.
- **Объём данных на экране.** 20 строк в день или 5000 — это меняет всю компоновку.

Если пользователь не отвечает — выбери сам, назови свой выбор вслух одной строкой и продолжай. Не тормози работу ради уточнений.

## Шаг 2. Дизайн-направление (обязательный шаг)

Прочитай `references/ui-directions.md`. Там каталог направлений, антипаттерны и правила вывода токенов из домена.

Затем прочитай `assets/design-log.md` — журнал того, что уже использовалось в прошлых проектах. **Направление, уже занятое другим проектом, брать нельзя.** Это и есть механизм, из-за которого проекты не сходятся к одному виду.

Выпиши токены до кода — коротко, 8–12 строк:

```
Домен:        автосервис, приём машин в ремонт
Направление:  «цеховой журнал» — плотная сетка, моноширинный шрифт для номеров
Палитра:      #12140F фон, #E8E4D9 текст, #C4451D акцент, #6B7A5A вторичный, #2A2D26 карточки
Шрифты:       display — Oswald (узкий, заглавные), body — Inter, data — JetBrains Mono
Сетка:        левая колонка 220px фикс, контент — двухпанельный (список + карточка)
Радиусы:      2px везде
Сигнатура:    строка машины в списке — как штрихкод: госномер моноширинно, цветная полоса статуса слева на всю высоту строки
```

Один сигнатурный элемент на проект. Всё остальное — тихое и дисциплинированное. Смелость тратится в одном месте, иначе интерфейс превращается в шум.

## Шаг 3. Проверка на шаблонность

Перед кодом прогони токены по списку из `references/ui-directions.md`, раздел «Антипаттерны». Если хоть один пункт совпал — переделай эту часть и скажи, что именно поменял и почему.

Главный тест: *«Если бы бриф был про доставку еды вместо автосервиса — я бы нарисовал то же самое?»* Если да — направление выведено не из домена, а из привычки. Переделывай.

## Шаг 4. Backend

Подробности и заготовки — `references/architecture.md`. Работа с данными, производительность и API — `references/data-and-api.md` (читать всегда, когда в проекте есть список записей или мобильный клиент).

**Два правила, которые не обсуждаются:**

1. **Операции над данными — только на сервере.** Пагинация, поиск, фильтрация, сортировка, итоги. Никогда не «загрузили всё и режем на клиенте»: на сотне записей это летает, на десяти тысячах браузер оператора встаёт — а данные к тому моменту уже боевые. Плюс то, что не должно быть видно, не должно и приходить. На клиенте остаётся только состояние интерфейса: что открыто, что выделено, что набрано в поле.
2. **API версионируется с первого дня.** `/api/v1/...`, отдельные каталоги контроллеров и ресурсов под версию. Причина: мобильное приложение у пользователя нельзя обновить принудительно, старая версия живёт в телефонах месяцами. Внутри версии допустимы только добавления.

Кратко по слоям:

- Route → Controller (тонкий, только оркестрация) → Service (бизнес-логика) → Repository (запросы к БД).
- Валидация только в Form Request. В контроллере — ни одного `$request->validate()`.
- Возврат данных в Inertia через DTO или API Resource, не голые модели.
- Enum'ы для статусов, не строки.
- Миграции с явными индексами по внешним ключам и по полям, по которым фильтруют.
- Pest-тесты на каждый сервис: happy path + минимум один отказ. Фичевый тест на каждый маршрут, меняющий данные.
- Права — Policy на модель, а не проверки внутри контроллера.

Типовые модули CRM (сущности, статусы, связи) — `references/modules.md`. Бери оттуда, но переименовывай под домен: в клинике это не «сделка», а «приём».

**Скорость — требование, а не оптимизация под конец.** CRM — инструмент, в котором человек проводит смену и открывает список двести раз. Работай по `references/performance.md` с самого начала: индексы под реальные запросы, поиск через `pg_trgm` вместо `LIKE '%…%'`, `select` только нужных колонок, курсорная пагинация на длинных лентах, тяжёлое — в очередь. Проверять скорость нужно на сидере с 50–100 тысячами записей: на тридцати тестовых быстро всё.

**Если у системы появляется второй потребитель** — мобильное приложение на Flutter, интеграция, бот, — то API создаётся **сразу версионированным** (`/api/v1`, `routes/api/v1.php`, `Controllers/Api/V1`). Читай `references/api.md`. Добавить версионирование задним числом нельзя: у приложения на телефонах пользователей нет кнопки «обновись немедленно», старая версия будет ходить на сервер месяцами. Дублируются только контроллеры, ресурсы и реквесты — сервисы остаются общими для всех версий и для веба.

## Шаг 5. Frontend

Стек фиксирован: **Laravel + Inertia + Vue 3 `<script setup>` + Tailwind.** Не предлагай Nuxt, отдельное SPA или API-клиент на фронте — выбор стека уже сделан, обсуждать его не нужно.

Два файла к прочтению перед кодом:

- `references/frontend-vue.md` — структура каталогов, постоянный layout, фильтры через URL с частичной подгрузкой (`only`), `useForm`, панель детали, массовое выделение, Reverb, файл токенов.
- `references/craft-baseline.md` — анатомия таблицы, состояния, тени, пустые состояния, чек-лист перед сдачей. Это планка, ниже которой отдавать нельзя.

Три правила, которые ломать нельзя:

- **Ни одной операции над данными на клиенте.** Поиск, фильтрация, сортировка, пагинация, итоги — всегда запрос на сервер с параметрами. `props.orders.filter(...)` в `computed` — ошибка: на демо с тридцатью записями это мгновенно, а через полгода эксплуатации список встаёт намертво. Подробности и граница «что всё-таки остаётся на клиенте» — `references/performance.md`.
- **Ни одного цвета мимо `tokens.css`.** `bg-blue-500`, `bg-slate-*`, `#hex` в шаблоне — ошибка. Иначе следующий проект не перекрашивается сменой одного файла, и все проекты сползают в одинаковый серо-синий.
- **Компоненты именуются под домен:** `RepairOrderRow`, а не `DataTableRow`. Название компонента — это тоже проектирование.

Перед сдачей пройди чек-лист из последнего раздела `craft-baseline.md`. Если хотя бы один пункт не выполнен — интерфейс не готов, независимо от того, насколько удачное направление выбрано.

## Что важно помнить

Пользователь этого скилла — разработчик, который сдаёт CRM разным заказчикам. Его конкурентное отличие в том, что его системы визуально узнаваемо не Bitrix и не очередная админка на готовом шаблоне. Backend можно и нужно унифицировать до предела — экономия времени там. UI унифицировать нельзя, иначе теряется весь смысл.
