# Производительность

CRM — инструмент, в котором человек живёт восемь часов. Список открывается двести раз за смену. Поэтому скорость здесь не «оптимизация под конец», а требование наравне с корректностью.

## 1. Главное правило: где выполняется операция

**Любая операция над набором данных выполняется на сервере.** Поиск, фильтрация, сортировка, пагинация, группировка, подсчёт итогов, экспорт — всё это SQL, а не JavaScript.

Клиент никогда не получает весь набор. Если на экране 25 строк — с сервера пришло 25 строк, а не 5000 «чтобы фильтровать быстро на фронте». Такой фронтовый фильтр кажется мгновенным на демо с тридцатью записями и намертво встаёт через полгода эксплуатации, когда записей стало сорок тысяч. Переделывать это в работающей системе дорого, поэтому делается правильно сразу.

Что **нельзя** писать в компоненте:

```js
// нет: фильтрация массива на клиенте
const found = computed(() => props.orders.filter(o => o.title.includes(query.value)))

// нет: сортировка полученного массива
const sorted = computed(() => [...props.orders].sort(byField(field.value)))

// нет: нарезка на страницы на клиенте
const page = computed(() => all.value.slice(offset, offset + 25))
```

Вместо этого — запрос с параметрами, как в `frontend-vue.md`: `router.get(..., { only: ['orders'], preserveState: true })`.

**Что остаётся на клиенте — и должно там остаться.** Правило выше про данные, а не про интерфейс. Гонять на сервер состояние интерфейса — вторая крайность, и тормозит она не меньше:

- открыта ли панель, какая вкладка активна, свёрнут ли сайдбар;
- какие строки выделены (`Set` в памяти);
- состояние формы до отправки;
- форматирование дат и сумм;
- оптимистичная отметка статуса — с откатом при ошибке.

Граница простая: **сервер владеет данными, клиент владеет видом.**

## 2. Поиск

`LIKE '%текст%'` не использует обычный индекс и на большой таблице читает её целиком. В PostgreSQL:

```php
// миграция
DB::statement('CREATE EXTENSION IF NOT EXISTS pg_trgm');
DB::statement('CREATE INDEX clients_name_trgm_idx ON clients USING gin (name gin_trgm_ops)');
```

Тогда `ILIKE '%иван%'` работает по индексу. Для поиска по нескольким полям сразу — материализованная колонка `tsvector` с GIN-индексом и обновлением через триггер или в сервисе.

Отдельные случаи, которые встречаются в каждой CRM:

- **Телефон.** Хранить нормализованную колонку `phone_normalized` (только цифры) с индексом и искать по ней. Иначе поиск по «555-26» не находит номер, записанный как «+1 (415) 555-2671».
- **Номер документа.** Точное совпадение и префикс (`LIKE '192%'`) — обычный btree-индекс, отдельная ветка в запросе, не общий полнотекстовый поиск.
- **Минимальная длина запроса** — 2–3 символа, иначе каждый первый символ запускает тяжёлый поиск.
- **Debounce 300ms + отмена предыдущего запроса.** Без отмены ответы приходят вразнобой и список моргает чужими результатами.

## 3. Пагинация и сортировка

- `paginate()` делает `count(*)` по всей выборке — на сотнях тысяч строк это дороже самой выборки. Для админских таблиц с номерами страниц это приемлемо до ~100k строк; дальше `simplePaginate()` (без общего числа) или курсор.
- `cursorPaginate()` — для длинных лент и бесконечной прокрутки: работает по индексу и не деградирует на дальних страницах. `OFFSET 50000` заставляет БД прочитать и выбросить 50000 строк.
- Сортировка разрешена только по списку допустимых колонок, и каждая такая колонка должна быть в индексе. Иначе пользователь одним кликом по заголовку кладёт базу.

```php
$allowed = ['created_at', 'total', 'status'];
$sort = in_array($request->sort, $allowed, true) ? $request->sort : 'created_at';
```

Это ещё и защита: подстановка имени колонки в `ORDER BY` из запроса без белого списка — дыра.

## 4. Запросы к БД

- **N+1 — главная причина медленных списков.** `with()` для связей, `withCount()` вместо подсчёта в шаблоне, `withSum()` для итогов. В деве включить `Model::preventLazyLoading()` — тогда N+1 падает с ошибкой, а не молча тормозит.
- **`select()` только нужных колонок.** Таблица заявок с полем `description` на 4 КБ: 25 строк — это 100 КБ, которые никто не читает в списке.
- **Индексы под реальные запросы**, а не «на всякий случай на каждое поле». Составной индекс покрывает запросы по своему префиксу: `(status, created_at)` работает и для фильтра только по `status`, но не для фильтра только по `created_at`.
- **Частичный индекс** для того, что фильтруют постоянно: `CREATE INDEX ... WHERE deleted_at IS NULL` или `WHERE status != 'closed'` — он в разы меньше и быстрее.
- **Агрегаты не считать на лету.** Долг клиента, сумма по сделкам, количество открытых заявок — денормализованные колонки, обновляемые в событиях. Считать `SUM` по всем оплатам при отрисовке каждой строки списка нельзя.
- `EXPLAIN ANALYZE` на каждый запрос списка перед сдачей. `Seq Scan` по большой таблице — повод для индекса.

## 5. Размер ответа

- Отдавать ровно поля, которые отрисовывает страница. Ресурс «на все случаи жизни» тянет связи, не нужные списку.
- Тяжёлые блоки (сводка, графики, счётчики) — `Inertia::defer()`, чтобы таблица появилась сразу, а сводка догрузилась.
- Справочники (статусы, сотрудники, услуги) — один раз в общих данных layout, а не в каждом ответе списка.
- Изображения: миниатюры генерируются при загрузке, в списке отдаётся миниатюра, а не оригинал на 3 МБ. `loading="lazy"` на строках таблицы.

## 6. Кэш

Redis, с понятной инвалидацией — иначе кэш станет источником багов «у меня старые данные».

- Справочники и настройки — по тегам, сброс в событии изменения.
- Блок сводки — короткий TTL (30–60 секунд). Цифра «выручка за месяц» не обязана быть посекундно точной, а считается тяжело.
- Права и роли пользователя — на время сессии.
- Не кэшировать сами списки записей: они меняются часто, а инвалидация по фильтрам нереализуема.

## 7. Тяжёлые операции

В очередь, всегда: импорт из Excel, экспорт, генерация документов, массовая рассылка, пересчёт итогов, отчёты за период. Пользователь получает уведомление о готовности и ссылку.

Импорт больших файлов — чанками (`LazyCollection`, `chunk`), с отчётом об ошибочных строках, а не «упало на 4000-й строке, начните заново».

Долгая операция в HTTP-запросе — это в лучшем случае 504 у оператора, в худшем — заблокированный воркер и вставшая очередь для всех.

## 8. Бюджеты и измерение

Числа, ниже которых интерфейс ощущается быстрым:

| Что | Цель |
|---|---|
| Ответ сервера на список | < 200ms |
| Запросов к БД на страницу списка | ≤ 10 |
| Реакция на нажатие в интерфейсе | мгновенная (оптимистично или блокировка кнопки) |
| Открытие панели детали | < 150ms |
| Первая отрисовка страницы | < 1s |

Как мерить, а не угадывать:

- Laravel Debugbar или Telescope в деве — видно число запросов и дубли.
- Логировать медленные запросы (> 200ms) в проде, смотреть раз в неделю.
- `Model::preventLazyLoading()` и `preventSilentlyDiscardingAttributes()` в `AppServiceProvider` для локальной среды.
- Тест на количество запросов для главных списков — он ловит N+1 при добавлении новой связи:

```php
it('отдаёт список заявок без N+1', function () {
    RepairOrder::factory()->count(30)->create();

    DB::enableQueryLog();
    $this->get(route('repair-orders.index'))->assertOk();

    expect(count(DB::getQueryLog()))->toBeLessThan(12);
});
```

Проверять скорость нужно на объёме, похожем на боевой: сидер, набивающий 50–100 тысяч записей. На тридцати тестовых записях быстро всё.
