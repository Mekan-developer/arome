# API и версионирование

Веб-часть CRM работает через Inertia и API не требует. API появляется, когда у системы есть второй потребитель: мобильное приложение (Flutter), интеграция с 1С или сайтом заказчика, телеграм-бот, внешний партнёр.

**Любой API создаётся сразу версионированным.** Добавить версионирование потом невозможно без ломки клиентов: у мобильного приложения на телефонах пользователей нет кнопки «обновись прямо сейчас», старая версия будет ходить на сервер месяцами.

## 1. Структура

Версия — в URL. Это самый простой вариант: видна в логах, в отладчике, в конфиге мобильного приложения, кэшируется отдельно. Версия в заголовке выглядит академичнее, но отлаживать её на устройстве заказчика тяжело.

```
routes/
├── api/
│   ├── v1.php
│   └── v2.php
app/Http/
├── Controllers/Api/V1/RepairOrderController.php
├── Resources/V1/RepairOrderResource.php
└── Requests/Api/V1/StoreRepairOrderRequest.php
```

```php
// bootstrap/app.php
->withRouting(
    api: __DIR__.'/../routes/api/v1.php',
    apiPrefix: 'api/v1',
)
```

**Дублируются только контроллеры, ресурсы и реквесты. Сервисы — никогда.** Бизнес-логика одна на все версии, разный только формат входа и выхода. Ровно ради этого и нужен слой Service: `Api\V1\RepairOrderController`, `Api\V2\RepairOrderController` и веб-контроллер для Inertia вызывают один и тот же `RepairOrderService`. Если логика начала расползаться по версиям — она утекла в контроллер, надо возвращать обратно.

## 2. Правило совместимости

Внутри опубликованной версии допустимы только **добавления**:

| Можно в существующей версии | Требует новой версии |
|---|---|
| Новое поле в ответе | Удалить или переименовать поле |
| Новый необязательный параметр | Сделать параметр обязательным |
| Новый эндпоинт | Изменить тип поля (`"12.50"` → `12.5`) |
| Новое значение enum, если клиент готов к неизвестным | Изменить смысл существующего поля |
| Расширить лимиты | Изменить структуру вложенности |

Клиент обязан игнорировать незнакомые поля — это пишется в документации и соблюдается в Flutter-приложении (парсинг по нужным ключам, а не строгая схема, падающая на лишнем поле).

Когда выходит v2: v1 продолжает работать минимум 6 месяцев, отвечает заголовками `Deprecation: true` и `Sunset: <дата>`, использование логируется. Отключать v1 можно, только когда в логах не осталось запросов.

## 3. Формат ответа

Один формат на весь API, без исключений.

```json
{
  "data": { "id": 192541, "number": "2026-192541", "status": "paid" },
  "meta": { "server_time": "2026-07-28T09:14:03Z" }
}
```

Список:

```json
{
  "data": [ ... ],
  "meta": {
    "per_page": 25,
    "next_cursor": "eyJpZCI6MTkyNTE2fQ",
    "has_more": true
  }
}
```

Договорённости, которые дешевле принять сразу:

- Ключи в `snake_case` — совпадают с БД, меньше поводов ошибиться.
- Даты в ISO 8601 с зоной (`2026-07-28T09:14:03Z`), всегда UTC. Локальное время — забота клиента.
- Деньги — целое число в минимальных единицах плюс код валюты: `{"amount": 152860, "currency": "TMT"}`. Числа с плавающей точкой для денег не использовать никогда.
- Идентификаторы в JSON — строкой, если они могут превысить 2^53: JavaScript-клиенты незаметно теряют точность на больших числах.
- `null` для пустого значения, не пустая строка и не отсутствующий ключ. Присутствие ключа стабильно.

## 4. Ошибки

Мобильный клиент должен реагировать на **код**, а не разбирать текст сообщения — иначе перевод интерфейса ломает логику.

```json
{
  "error": {
    "code": "order_already_closed",
    "message": "Заказ-наряд уже закрыт",
    "fields": { "status": ["Недопустимый переход статуса"] }
  }
}
```

Коды: `200` успех, `201` создано, `422` ошибки валидации (`fields` заполнено), `401` не аутентифицирован, `403` нет прав, `404` не найдено, `409` конфликт состояния, `429` превышен лимит.

Доменные исключения из сервисов преобразуются в коды в одном месте (обработчик исключений), а не `try/catch` в каждом контроллере.

## 5. Аутентификация

- Мобильное приложение — Laravel Sanctum, токен на устройство, с именем устройства и датой последнего использования. Отзыв токена — по устройству, чтобы «выйти на потерянном телефоне» работало.
- Внешние интеграции — отдельный токен со своими правами и своим лимитом запросов.
- Ограничение частоты — обязательно: `throttle:60,1` по умолчанию, отдельные лимиты на вход и на поиск.
- Права — те же Policy, что и в вебе. Дублировать проверки для API нельзя, разъедутся.

## 6. Списки

Правила из `performance.md` действуют и здесь, с усилением: мобильный клиент часто сидит на медленной сети.

- Курсорная пагинация по умолчанию: `?cursor=...&per_page=25`, максимум 100.
- Фильтры — явные параметры (`?status=paid&from=2026-07-01`), белый список сортировок.
- Поддержка выборочных полей (`?fields=id,number,status`) для экономии трафика на списках.
- Дельта-синхронизация для офлайн-режима: `?updated_since=...` плюс отдача удалённых id, иначе на устройстве останутся записи-призраки.
- `ETag` / `If-None-Match` на справочниках — приложение не качает неизменившийся список услуг при каждом запуске.

## 7. Вывод версии из обращения

Версия — это не «v1 навсегда, потом v2 когда-нибудь». Правило: **новая версия создаётся только когда ломается совместимость**, и не чаще. Плодить v3, v4 на каждое изменение — способ получить четыре набора контроллеров и ни одного поддерживаемого.

Признак, что пора: понадобилось изменить структуру ответа так, что старое приложение перестанет её понимать. Всё остальное решается добавлением.

## 8. Минимальная версия клиента

Отдельный лёгкий эндпоинт, который приложение дёргает при запуске:

```
GET /api/v1/app/requirements
{ "min_version": "1.4.0", "recommended_version": "1.7.2", "message": "..." }
```

Позволяет мягко просить обновиться и жёстко блокировать версии с критической ошибкой. Без этого единственный способ снять с эксплуатации старую версию — ждать.

## 9. Тесты и документация

- Feature-тесты на каждый эндпоинт каждой версии, отдельными файлами: `tests/Feature/Api/V1/`. Тесты v1 не редактируются при разработке v2 — они и есть гарантия, что v1 не сломан.
- Проверять в тесте не только статус, но и структуру ответа (`assertJsonStructure`) — именно она является контрактом.
- Документация генерируется из кода (Scribe или OpenAPI-атрибуты) и лежит рядом с версией. Документация в отдельном документе устаревает за месяц.
- Коллекция запросов (Postman/Bruno) в репозитории — тому, кто пишет Flutter-клиент, это экономит день.
